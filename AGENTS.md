* Use the [GLOSSARY.md](docs/src/content/GLOSSARY.md) and documentation in this repository (e.g., [`README.md`](README.md)) to understand how this tool is intended to be used and developed.
* In repository Markdown files, link every mention of a term defined in [GLOSSARY.md](docs/src/content/GLOSSARY.md) back to the glossary.
* Update [`CHANGELOG.md`](CHANGELOG.md) when making changes to any of the modules within this repository. Do not add entries for changes made to files relating to the documentation, local development environment, or continuous integration pipeline. If you don't know what release you are contributing to, see if the latest release in the [`CHANGELOG.md`](CHANGELOG.md) is published. If it is not, that may indicate you are helping with a new release that will be based the `main` branch. If you are working on a feature branch, it is safe to assume that feature branch will be merged to `main` before the release is published. If it's easier to just ask the user instead of picking or inventing one, do that. When you update software, identify its previous version and its new version in changelog entry.
* Read [STATE_MACHINES.md](STATE_MACHINES.md) and [SCHEMA.md](SCHEMA.md) along with [GLOSSARY.md](docs/src/content/GLOSSARY.md). If they disagree, the glossary takes precedence over the schema, and the schema takes precedence over the state machines. Report disagreements.
* Treat items marked “Ask” in [STATE_MACHINES.md](STATE_MACHINES.md) as open questions to raise with the [user](docs/src/content/GLOSSARY.md#user), not rules to follow.
* Regenerate [schema/mappings.schema.json](schema/mappings.schema.json) with `finch get schema` whenever the model types change. In a checkout, run `cargo run --quiet -- get schema > schema/mappings.schema.json`.
